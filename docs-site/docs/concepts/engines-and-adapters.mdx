An engine is the rented inner loop. UseAgent does not build the agent that decides
what to do; it drives an existing one and owns everything around it.

## Engine

The coding-agent runtime that decides what to do and emits native activity.
OpenCode runs a resident `opencode serve`; Pi uses a persistent JSONL session
through an RPC bridge; selected Codex, OpenCode, and Claude traffic can use the
orchestration runtime; and Codex or Claude can fall back to the resident ACP
compatibility path. The direct `chat` engine calls the model without a sandbox.

## Provider driver

The typed lifecycle boundary in `@useagent/agent-harness`. A driver declares its
protocol and session generation, supported lifecycle operations and steer input
kinds, model policy, tool mode, and capability map. The validator checks that
those declarations agree. For example, a driver cannot advertise resume or
per-turn model selection without the matching lifecycle operation. Unsupported
operations return a classified result. Backend adapters connect supported
operations to sandboxes and native protocols.

## Current execution paths

There are several execution paths because engines expose different native
interfaces:

Selection of the runtime path is operator-gated: `RUNTIME_RUN_ADAPTER_ENABLED`
turns it on (off unless `1` or `true`), and `RUNTIME_RUN_ADAPTER_MODE` chooses
`canary`, which uses a thread and run allowlist, or `all`
(`backend/src/engines/runtime-adapter.ts`). With no
`RUNTIME_RUN_ADAPTER_ENGINES` list configured, the runtime lane covers codex and
opencode while claude stays on the ACP compatibility path. Deployment
configuration decides whether the gate is enabled; source code alone does not
establish the current production mode.

The production worker resolves an engine registry before each turn. Native
OpenCode and selected runtime-path routes receive a concrete `ProviderDriver`;
ACP Claude and Codex execution is declared as an `EngineAdapter`
compatibility path.

:::note
**Naming.** Modules are named by function, so the runtime path is named for what
it does, not for a vendor. A vendored protocol name appears only at true wire
boundaries, such as the provider driver and the frame parsers that speak an
engine's actual protocol.
:::

## Codex subscription relay

A one-use, run-bound WebSocket capability. It lets a managed ChatGPT
subscription drive a run without ever copying OAuth state into the sandbox: the
Codex app-server and the ChatGPT OAuth stay on the trusted backend, while only
the Codex exec-server runs inside Cube or Daytona.

The relay has focused tests for grant consumption and runtime behavior. A live
deployment still needs its own readiness check; source code alone does not prove
an active subscription connection.

## Engine readiness is credential-mode aware

A release proves the path that matches how an engine authenticates. A
subscription-only Codex release proves the connected account and the native turn
path; an API-key engine proves its mapped gateway provider. Readiness checks do
not assume a single credential shape across engines.

## Session authority

The backend persists more than a native session id. A provider-session binding
also records the provider, runtime, protocol identity, session generation, and a
credential epoch when the session depends on a connected account. Resume,
cancel, and recovery resolve a driver only when that complete binding still
matches. Stale generations, changed subscription credentials, and ambiguous
legacy sessions fail closed.
