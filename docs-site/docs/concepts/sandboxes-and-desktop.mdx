Sandbox-backed engines work inside an isolated workstation. The backend
provisions it, sends turns, and records the activity it receives. The direct
`chat` engine does not use a sandbox.

## Sandbox

The isolated Linux workstation where agent commands, repositories, browser
automation, desktop apps, and recordings run. A thread gets one sandbox and one
working directory, retained and reused across its runs: the lease checks
liveness and required labels before reuse and re-provisions when the retained
sandbox is stale (`backend/src/engines/thread-sandbox.ts`). A run executes
inside its thread's sandbox.

## Sandbox provider

A vendor-specific implementation selected behind a provider-neutral sandbox
contract. **Daytona** and **Cube** expose the same required process, filesystem,
PTY, preview, and lifecycle boundary, then keep provider-specific behavior and
tests for native capabilities. Code above the contract does not branch on the
provider.

### Provider configuration

| Variable | Required | Default / purpose |
| --- | --- | --- |
| `SANDBOX_PROVIDER` | No | `daytona`; accepts `daytona` or `cube`. |
| `DAYTONA_API_KEY` | For Daytona | API credential for the Daytona control plane. |
| `DAYTONA_API_URL` | No | `https://app.daytona.io/api`. |
| `DAYTONA_TARGET` | No | `us`. |
| `CUBE_API_URL` | No | `http://127.0.0.1:3000`. |
| `CUBE_API_KEY` | Deployment-specific | Passed to Cube when configured. |
| `CUBE_TEMPLATE_ID` | For Cube | Template used to create the workstation. |
| `CUBE_SANDBOX_DOMAIN` | No | `cube.app`; must be a DNS hostname. |
| `CUBE_PROXY_TRUSTED_INGRESS` | No | Enables public sandbox traffic only for a trusted ingress proxy. |

Cube's E2B-compatible public proxy must use the normal port for its scheme:
port 80 for HTTP or 443 for HTTPS. Set `CUBE_PROXY_SCHEME` and
`CUBE_PROXY_PORT_HTTP` only when the deployment differs from the defaults. The
adapter rejects mismatched scheme and port pairs at startup.

## Warm pool

Prepared sandboxes kept ready so a new run avoids most cold-start work. Warm-pool
claimable creation and parallelized post-sandbox preparation are part of the
turn-start latency effort.

## Desktop

The visible XFCE and Chromium workstation shown through noVNC. Readiness is
strict: it requires the noVNC page, RFB, XFCE, browser CDP, and both CDP relays.
Daytona can drive the desktop natively, while Cube uses trusted X11 controls. An
engine controls it through the desktop computer-use tools, and desktop recording
publishes a real MP4 artifact.

## Restart reconciliation

Because the sandbox runs independently of the backend, a backend restart does not
necessarily kill its resident process. Recovery depends on the selected engine:

<Steps>
  <Step title="The sandbox keeps executing">
    The workstation process may continue through a backend bounce.
  </Step>
  <Step title="A recovery loop re-probes">
    On restart, a background loop finds in-flight sessions and asks the selected
    driver for its observed state. Drivers without reconciliation support cannot
    provide the same adoption path.
  </Step>
  <Step title="The real result is adopted">
    A supported driver can report completion or interim activity. The backend
    records the adopted result or settles the run with an explicit failure.
  </Step>
</Steps>

The boot pass settles the commands mailbox, then the recovery loop re-probes
supported sessions with visible reconciling heartbeats until it can adopt a
result or reaches its deadline.

:::warning
The sandbox contract does not expose explicit pause, checkpoint, or snapshot
operations. Recovery re-probes supported live engines; it does not restore a
saved machine image.
:::
