Run these commands from the repository root unless a step says otherwise.

## 1. Prepare the database

Install Bun and run Postgres with the `vector` extension available. Create a
development database named `useagent`, or use another name in `DATABASE_URL`.

The backend applies committed Drizzle migrations on startup. Its database role
must be able to apply those migrations; pgvector must be installed on the
server before a migration can enable the extension.

:::note
Use a database dedicated to this local stack. Only one backend per database is
supported. `REQUIRE_SINGLE_BACKEND=true` makes the startup guard refuse a second
backend; without that flag it only warns. See [operational invariants](/operations/invariants).
:::

## 2. Install dependencies

The apps and shared packages have separate package manifests and lockfiles.
Install the shared packages first, then the apps:

```bash
for package in packages/*/; do
  (cd "$package" && bun install)
done
(cd backend && bun install)
(cd frontend && bun install)
```

The docs site is optional for running the product:

```bash
(cd docs-site && bun install)
```

## 3. Set the local environment

Add the following to `backend/.env`, adapting the database connection for your
machine. Preserve any existing settings you still need.

```dotenv
DATABASE_URL=postgres://postgres@localhost:5432/useagent
PORT=3201
FRONTEND_ORIGIN=http://localhost:3400
BETTER_AUTH_URL=http://localhost:3400
REQUIRE_SINGLE_BACKEND=true
```

Set the frontend origin explicitly: the backend's default is port `3200`, while
the frontend's current dev script uses `3400`. Using the frontend origin for
`BETTER_AUTH_URL` keeps browser authentication on the proxied app origin.

In development, the backend can use a seeded user and organization for requests
without a session. `ALLOW_DEV_ORG=0` disables that fallback. The development
auth-secret fallback is for local use; configure a real `BETTER_AUTH_SECRET`
and disable development mode before exposing a deployment.

The loopback operator bridge stays disabled unless `USEAGENT_OPERATOR_SECRET`
is set to an independent random value of at least 32 characters. Do not reuse
`BETTER_AUTH_SECRET`.

### Model and sandbox access

| Capability | Additional configuration |
| --- | --- |
| Direct chat | A model provider credential; the environment-backed path uses `OPENROUTER_API_KEY` |
| Daytona sandboxes | `SANDBOX_PROVIDER=daytona` and `DAYTONA_API_KEY` |
| Cube sandboxes | `SANDBOX_PROVIDER=cube` plus the endpoint, template, and provider configuration described in [Sandboxes](/concepts/sandboxes-and-desktop) |
| Additional coding engines | An enabled engine and a supported connected account or provider credential |
| Optional team-memory service | `MEMORY_API_URL` and the service's access configuration |

A sandbox key alone does not make every engine ready. Check
[provider connections and models](/platform/provider-connections-and-models)
for account setup and readiness.

## 4. Start both apps

In one terminal:

```bash
bun run dev:backend
```

In another:

```bash
bun run dev:frontend
```

Open `http://localhost:3400`. Check the backend separately with:

```bash
curl http://localhost:3201/api/health
```

The health response is `{"status":"ok"}`. It confirms the API is listening,
not that a provider account or sandbox is ready. Try a small task through the
workspace after configuring the relevant connection.

## Troubleshooting

| Symptom | Check |
| --- | --- |
| Backend fails during migration | Database connectivity, role permissions, and the installed pgvector extension |
| A second backend refuses to boot | Stop the other local backend or use a different database |
| Authentication rejects the browser origin | Match `FRONTEND_ORIGIN` and `BETTER_AUTH_URL` to `http://localhost:3400` |
| The UI loads but API requests fail | Backend port; `USEAGENT_API_ORIGIN` in the frontend environment if you changed it |
| Chat or agent work fails | The selected model, enabled engine, provider connection, and sandbox readiness |

## Check your changes

```bash
bun run typecheck
```

This checks the frontend, backend, and shared packages. See
[verification](/operations/verification) for targeted tests and docs checks.
