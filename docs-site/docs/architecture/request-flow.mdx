This is the life of a single agent turn, following the units from
[Runs, threads, and commands](/concepts/runs-threads-commands).

## From prompt to timeline

<Steps>
  <Step title="A command is accepted">
    A prompt from the web app, Slack, or an automation becomes a durable command.
    Callers may add an idempotency key for safe retries. It enters the command
    lane every channel shares.
    A thread admits one in-flight turn at a time; additional prompts, including
    gateway child-session requests, queue durably in the commands mailbox and
    dispatch serially per thread under a per-thread advisory lock.
  </Step>
  <Step title="A run is created">
    The backend creates a run inside a thread. A sandbox-backed reply reuses the
    thread's workstation when it is still valid. A new sandbox-backed thread
    claims or creates a sandbox. The `chat` engine skips this step.
  </Step>
  <Step title="The turn reaches the selected engine">
    The engine registry resolves a `ProviderDriver` for the engine, and the turn
    is dispatched to its registered execution path. Current paths include native
    OpenCode, Pi over its RPC bridge, selected Codex/OpenCode/Claude sessions over
    the orchestration runtime, and ACP compatibility for Codex or Claude. The
    `chat` engine calls the model directly without a sandbox. Engine capability
    maps describe which controls and timeline surfaces are available.
  </Step>
  <Step title="Privileged work goes through the gateway">
    When the engine needs to read a repository, search knowledge, use the desktop,
    or publish an artifact, it calls a gateway tool bound by a short-lived
    capability token. A destructive operation pauses on a durable approval
    request with a 15-minute TTL (pending, then approved, denied, or expired). A
    human resolves it through `/api/gateway/approvals`, and the agent polls out
    a one-shot capability bound to the exact run, tool, and normalized
    arguments. That capability expires after at most two minutes. See [Gateway tools and
    approvals](/concepts/gateway-tools-and-approvals).
  </Step>
  <Step title="Output is recorded and projected">
    The worker records steps and native provider frames during the turn. After
    finalization, the canonicalization outbox builds the provider-neutral event
    projection used by the session UI.
  </Step>
  <Step title="The timeline renders live">
    The session view subscribes to the thread stream, reduces steps into state,
    and renders each as a card or row. A reconnect receives a fresh durable
    snapshot.
  </Step>
  <Step title="The run finalizes">
    On completion the run writes its terminal state and any follow-up work to the
    outbox in the same transaction, then workers deliver canonicalization, Slack
    updates, and learning capture.
  </Step>
</Steps>

## Direct chat uses the same entry point

The product composer exposes `chat` as a no-sandbox engine. It still creates a
durable command and run, so direct conversation and sandbox-backed work share a
thread entry point and session UI. The older stateless `/api/chat` SSE route is
still mounted as a rollback surface, but the app root redirects to `/agent/new`.

:::tip
Choose `chat` for a model answer and a sandbox-backed engine when the task needs
files, a terminal, repositories, or a desktop.
:::

## Reconnection and recovery

Two mechanisms cover different failure modes:

- **Thread stream reconnect** hands back a fresh durable snapshot, so a dropped
  browser connection resyncs cleanly.
- **Restart reconciliation** re-probes an in-flight sandbox session when the
  selected driver supports it. Pi currently resumes settled session history but
  does not reconstruct an in-flight reconciliation stream. See
  [Sandboxes](/concepts/sandboxes-and-desktop#restart-reconciliation).
