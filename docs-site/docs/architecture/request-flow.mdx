This is the life of a single agent turn, following the units from
[Runs, threads, and commands](/concepts/runs-threads-commands).

## From prompt to timeline

<Steps>
  <Step title="A command is accepted">
    A prompt from the web app, Slack, or an automation becomes a durable command
    with an idempotency key. It enters the one command lane every channel shares.
    A thread admits one in-flight turn at a time; additional prompts, including
    gateway child-session requests, queue durably in the commands mailbox and
    dispatch serially per thread under a per-thread advisory lock.
  </Step>
  <Step title="A run is created">
    The backend creates a run inside a thread and acquires its sandbox. A reply
    reuses the thread's retained sandbox and working directory; a root run claims
    a fresh sandbox, preferably from the warm pool.
  </Step>
  <Step title="The sandbox is prepared for this turn">
    On a fresh sandbox using the T3-backed runtime path, the backend first
    installs and verifies the selected native provider and its stable settings.
    It then prepares authorized
    repositories, pull-request resources, and uploaded inputs. Only after those
    resources finish does it activate run-bound gateway capabilities, relays, or
    process leases. Short-lived run credentials are therefore not minted before
    a long clone, and a failed resource preparation creates no activation lease.

    Pi has a separate resources-first preparation path. Retained sandboxes keep provider
    preparation and resource validation in parallel where the runtime ownership
    contract allows it. These preparation differences do not change the native
    drivers of Codex, Claude Code, OpenCode, or Pi. ACP is not a fallback.
  </Step>
  <Step title="The turn reaches its native engine session">
    The engine registry resolves a `ProviderDriver` for the engine, and the turn
    is dispatched to the thread's native runtime inside the sandbox: Codex,
    Claude Code, and OpenCode through T3, and Pi through its RPC bridge.
    There is no generic ACP execution lane.
    The engine works in its own directory and starts emitting native events.
  </Step>
  <Step title="Privileged work goes through the gateway">
    When the engine needs to search knowledge, use the desktop,
    or publish an artifact, it calls a gateway tool bound by a short-lived
    capability token. A destructive operation pauses on a durable approval
    request with a 15-minute TTL (pending, then approved, denied, or expired). A
    human resolves it through `/api/gateway/approvals`, and the agent polls out
    a one-shot capability bound to the exact run, tool, and normalized
    arguments. See [Gateway tools and
    approvals](/concepts/gateway-tools-and-approvals).
  </Step>
  <Step title="Output is canonicalized into steps">
    Native events are translated into canonical steps and appended to the event
    log, with native frames retained for fidelity.
  </Step>
  <Step title="The timeline renders live">
    The session view subscribes to the thread stream, reduces steps into state,
    and renders each as a card or row. A reconnect receives a fresh durable
    snapshot.
  </Step>
  <Step title="The run finalizes">
    On completion the run writes its terminal state and any follow-up work to the
    outbox in the same transaction, then workers deliver canonicalization, Slack
    updates, and learning capture.
  </Step>
</Steps>

## Promote a chat into a run

The lightweight chat surface at the app root is a **no-sandbox** surface: it
streams answers over SSE with read-only knowledge, wiki, and memory retrieval
cited inline. When a conversation needs real work, it can be **promoted into a
full agent run**, which then follows the flow above with a sandbox and engine.

:::tip
The chat surface and the agent run share retrieval and rendering primitives, so a
promotion continues the same conversation rather than starting over.
:::

## Reconnection and recovery

Two independent mechanisms keep a turn durable:

- **Thread stream reconnect** hands back a fresh durable snapshot, so a dropped
  browser connection resyncs cleanly.
- **Restart reconciliation** re-probes an in-flight sandbox session after a
  backend bounce and adopts the real result. See
  [Sandboxes](/concepts/sandboxes-and-desktop#restart-reconciliation).
