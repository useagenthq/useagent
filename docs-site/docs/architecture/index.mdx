UseAgent separates product control from agent execution. The backend owns
identity, commands, records, policy, and delivery. A sandbox provides the
workstation. An engine runs inside that workstation. The frontend renders the
state exposed by the backend.

## The four properties

<CardGroup cols={2}>
  <Card title="Verify-gated" icon="shield-check">
    Verification is an evidence discipline, not self-grading: a conformance
    suite, environment-gated live proofs, and evidence recorded in the event
    log. Destructive gateway operations gate on a durable human approval lane
    with one-shot capabilities. A runtime verify stage on run completion is a
    design goal, not current behavior.
  </Card>
  <Card title="Durable records" icon="database">
    Commands, runs, steps, native frames, canonical events, approvals, and
    follow-up work are stored in Postgres. Some records are append-only; others
    are updated or rebuilt as a run settles.
  </Card>
  <Card title="Replaceable-engine" icon="plug">
    The inner loop sits behind a provider driver. OpenCode, Pi, Codex, and Claude
    share run and event contracts even though their native capabilities differ.
  </Card>
  <Card title="Actors" icon="box">
    Each sandbox-backed thread keeps a workstation and working directory on a
    per-thread lease. Each run is one turn. The direct `chat` engine uses the
    durable command lane without claiming a sandbox.
  </Card>
</CardGroup>

## Control outside, execution inside

The trusted backend owns admission, org scoping, capability tokens, storage,
workers, and SSE delivery. Engine processes and some engine-specific session
machinery are resident inside the sandbox, including `opencode serve`, the ACP
relay, the Pi bridge, or the selected orchestration runtime. The browser talks to
the product APIs and renders persisted snapshots plus live updates.

The consequences are concrete:

- An interrupted run can be **reconciled after a backend restart** when its
  engine exposes a supported recovery path. The backend re-probes the resident
  session and records the adopted result.
- Different engines render through **one UI contract**, because their
  native output is durably stored first, then translated into one
  provider-neutral canonical schema by a post-finalize outbox worker, and
  canonical events are persisted before they are published to subscribers.
- Long-lived platform credentials stay behind the **gateway**. Privileged work goes through the
  [gateway](/concepts/gateway-tools-and-approvals), reached only with a
  short-lived signed run token. Production defaults to `gateway_only` secret
  delivery. Development can use a compatibility mode that injects approved
  non-provider tooling secrets and records a names-only marker.

:::note
This is not strict event sourcing. Provider frames may be revised, steps may be
updated, and a finalized canonical projection may replace earlier rows. The
durability claim is narrower: accepted commands and settled product records are
stored, and the UI can resync from them.
:::
