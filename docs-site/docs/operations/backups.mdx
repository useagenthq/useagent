Backups are an operator responsibility in this checkout. The repository does
not include the previously documented `useagent-backup.sh` script or its daily
systemd timer. Configure a backup job for your actual storage and deployment.

## What to preserve

| Data | Why it matters |
| --- | --- |
| Postgres database | Threads, runs, events, account records, knowledge, and artifact metadata |
| Artifact storage | Published file bytes; `ARTIFACT_STORAGE_DIR` defaults to `backend/.artifacts` |
| Required local run data | `RUNS_ROOT` defaults to `backend/.runs`; inspect your runtime's use of these files |
| Service configuration | Database connections, public origins, provider settings, and enabled runtime features |
| Encryption and signing material | Existing encrypted records must remain readable after a restore |
| Separately hosted services | Optional memory storage and any durable sandbox/provider data have their own lifecycle |

The reference bootstrap writes configuration under `/etc/useagent`. Your
deployment may use different paths or a secret manager; inventory the actual
locations rather than assuming the reference layout.

## Establish a backup routine

1. Capture a consistent Postgres backup and the artifact files it references.
2. Preserve the configuration and key material required to read that data.
3. Encrypt archives, restrict access, and copy them off the application host.
4. Define retention and alert on failed or missing backups.
5. Record the application revision and backup timestamp.

If you need a consistent database-and-files checkpoint, quiesce writes while
taking it or use a coordinated storage snapshot. A database dump alone does
not contain published file bytes.

## Prove that restore works

Restore into a separate database and storage location first:

- Make pgvector available and restore the schema and records.
- Restore artifact files with permissions suitable for the backend and gateway.
- Recreate database roles and provide the required configuration and keys.
- Start one backend against the restored database.
- Sign in, open an existing thread, and download a known artifact.
- Check any separately hosted memory or sandbox resources.

Do not equate a successful restore with resuming every previously active run.
A remote sandbox or native engine session may no longer exist.

Record the result and measured recovery time. Rehearse again when storage,
encryption, authentication, or runtime deployment changes.
