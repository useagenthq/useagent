Use local checks for code and contract changes. Use configured, isolated
runtime environments for provider and sandbox behavior.

## Local checks

Run these commands from the repository root:

| Command | Coverage |
| --- | --- |
| `bun run typecheck` | Frontend, backend, and shared packages |
| `cd frontend && bun run lint` | Frontend lint rules |
| `cd frontend && bun run test` | Component tests under `components/` |
| `cd packages/conformance && bun run test` | Client and harness contract tests |
| `cd docs-site && bun run doctor` | Docs configuration and content checks |
| `cd docs-site && bun run build` | Static docs generation and search assets |

Run a relevant individual test file when making a focused change. Typecheck or
build success does not establish runtime parity or visual correctness.

## Backend tests use a disposable database

```bash
cd backend
bun run test
```

This script runs `test/prepare-db.ts`, which **drops and recreates
`useagent_test`** on the server selected by `TEST_ADMIN_URL`. The default admin
connection is local Postgres. It then runs the main suite and runs Slack tests
separately after another database reset.

Use a test-only database server and check the configured connection first.
Do not point this test command at a shared server containing data you need.
The preload in `backend/bunfig.toml` configures the test environment.

## Runtime journeys

| Command | Purpose |
| --- | --- |
| `cd backend && bun run e2e` | Full-stack test harness |
| `cd backend && bun run e2e:real` | Real provider and sandbox journeys |
| `cd backend && bun run soak` | Repeated workload and recovery scenarios |
| `bun backend/test/e2e/ui-sweep/sweep.ts` | Browser checks of product surfaces |

Read each harness's configuration and required credentials before running it.
Live journeys can create sandboxes, runs, and external resources. Keep their
database and provider resources isolated and clean them up afterward.

## Verify the behavior you depend on

For an engine or provider change, a useful live check includes:

1. A new task through the intended credential mode.
2. A follow-up in the same thread.
3. Reconnection to the session's recorded history.
4. The specific tool or artifact workflow affected by the change.

Record the engine, model, credential mode, runtime version, and outcome with
the evidence. A successful task on one engine does not certify every engine.

For a docs change, check internal links, search, desktop and narrow layouts,
and light and dark themes after the build.

Source: the root, frontend, backend, conformance, and docs-site
`package.json` files; `backend/test/prepare-db.ts`; and `backend/bunfig.toml`.
