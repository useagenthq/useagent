The checked-in bring-up path is `infra/self-host/deploy-app.sh`, with a Hetzner
reference host under `infra/self-host/hetzner/`. The script connects over SSH,
copies source, installs dependencies, builds the frontend, and writes systemd
and Caddy configuration.

## Prepare a host

The reference setup targets Ubuntu 24.04 with Bun, Node, Docker, PostgreSQL 16,
pgvector, and Caddy. The reference cloud-init pins Bun to 1.3.14. The deploy
script expects root SSH access and the provisioning marker `/opt/useagent-provision/READY`; use the reference cloud-init setup or
provide equivalent provisioning.

The control plane and sandbox fleet are separate. This core script does not
provision the optional memory service or a complete sandbox runtime.

## Bring up the core stack

From the repository root, set the host and database credentials in your shell,
then invoke the script:

```bash
SERVER_IP=<host-ip> \
PUBLIC_ORIGIN=https://useagent.example.com \
PG_PASSWORD=<app-database-password> \
PG_GATEWAY_PASSWORD=<gateway-database-password> \
BETTER_AUTH_SECRET=<stable-auth-secret> \
SECRETS_ENCRYPTION_KEY=<stable-encryption-key> \
USEAGENT_OPERATOR_SECRET=<stable-operator-secret> \
OPENROUTER_API_KEY=<provider-key> \
BOOTSTRAP_ADMIN_EMAIL=owner@example.com \
BOOTSTRAP_ADMIN_PASSWORD=<initial-admin-password> \
infra/self-host/deploy-app.sh /path/to/useagent
```

`SSH_KEY` optionally selects the SSH private key. Both database passwords are
required by the script. The three application secrets must be independent and
at least 32 characters long; generate them separately and reuse them on redeploy.
Use URL-safe database passwords. `PUBLIC_ORIGIN` must be a public HTTPS DNS
origin without a path or port. Point DNS at the host and allow ports 80 and 443
before deploying.

On a fresh database, supply both bootstrap admin fields; the password must be
at least 12 characters. The script creates the first user through a temporary
auth process after backend health succeeds, then removes its transient
credential file. Omit these fields on later deploys. Public signup stays off.

### What the script writes

| Location | Purpose |
| --- | --- |
| `/opt/useagent/` | Backend, frontend, and shared package source |
| `/etc/useagent/backend.env` | Database, stable secrets, public origins, production mode, and provider settings |
| `/etc/useagent/gateway.env` | Restricted gateway database connection |
| `useagent-backend.service` | Starts the Bun backend |
| `useagent-frontend.service` | Starts the built Next.js app on port 3400 |
| `/etc/caddy/Caddyfile` | HTTPS reverse proxy to the frontend |

Caddy obtains and renews TLS for the configured domain. The backend runs with
`NODE_ENV=production` and `USEAGENT_DEV_MODE=false` by default. A disposable
development host can explicitly opt in with `USEAGENT_DEV_MODE=true`. The
script installs the supplied secrets instead of regenerating them.

Environment files are written with mode `0600`. Re-running the script replaces
its generated environment and service files, so preserve any additional host
configuration and use the same stable keys.

## Configure the deployment

Before exposing the app to real users:

- Verify the public domain, HTTPS proxy, `FRONTEND_ORIGIN`, and `BETTER_AUTH_URL`
  generated from `PUBLIC_ORIGIN`.
- Keep production mode enabled and set `ALLOW_DEV_ORG=0` explicitly if managing
  environment settings outside the bootstrap.
- Set `REQUIRE_SINGLE_BACKEND=true` and run one backend against each database.
- Configure the sandbox provider and the engines/accounts you want to make available.
- Configure and start the dedicated gateway when sandbox tools need it. Writing
  `gateway.env` does not start that service.
- Put artifacts and other durable local data on persistent storage, and define
  a backup schedule.

The gateway validates independent `PROVIDER_GATEWAY_SECRET`,
`TOOL_GATEWAY_SECRET`, and `SECRETS_ENCRYPTION_KEY` values. Its production process
requires `GATEWAY_DATABASE_URL`; its public origin must be reachable by the
sandboxes. See [trust and control](/features/trust-and-control).

## Check the result

```bash
curl https://your-useagent-host/api/health
```

The script checks backend health, service activity, and public HTTPS health.
Then sign in as a provisioned user, check account readiness, run a small task,
and open its output.
A passing health check proves the HTTP service is up, not that model access,
sandbox tools, or artifact delivery work.

## Releases after bootstrap

The root `package.json` currently exposes development and typecheck scripts.
It does not expose the older `release:hosted`,
`release:provider-connection-bootstrap`, or `stage:t3-dist` commands.

The bootstrap script does not provide an immutable-image promotion pipeline,
automated parity certification, or automatic rollback. Use your deployment's
release procedure and preserve the previous build, configuration, and data
before a change. Next.js development and production builds use separate output
directories (`.next` and `.next-build`), but that alone is not a release pipeline.
