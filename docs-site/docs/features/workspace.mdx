Sandboxed engines do work inside an isolated Linux computer. Chat is the
exception: it is a no-sandbox, read-only conversational surface. For a
sandboxed thread, the backend retains a filesystem and working directory across
turns and exposes terminal, desktop, recording, and repository controls only
when the selected provider/runtime capability is ready.

## One workstation per thread

A thread acquires one sandbox and one working directory, retained and reused
across its runs on a per-thread lease. The lease checks liveness and required
labels before reuse and re-provisions when the retained sandbox is stale
(`backend/src/engines/thread-sandbox.ts`). Replies therefore land in the same
checkout with the same state, which is what makes multi-turn engineering work
feel continuous instead of starting over.

The sandbox vendor sits behind a provider-neutral contract. **Box**, **Cube**,
and **Daytona** implement the required process, filesystem, preview, and
lifecycle boundary and declare optional surfaces independently. Box's desktop
uses its native API; its interactive terminal uses the server-side Box CLI and
is unavailable when that prerequisite is missing. Warm pools are used only
where the configured provider and runtime support them.

## A desktop you can watch

When desktop capability is ready, the product opens the provider's workstation
through the authenticated desktop proxy. Desktop computer use, screenshots,
recording, and guarded login controls are advertised only when the current run
supports them. A completed recording can be published as an MP4 artifact; the
live desktop connection itself is not a replayed canonical event. See
[Sandboxes and desktop](/concepts/sandboxes-and-desktop).

## Repositories without pasted tokens

GitHub arrives through the platform integration, not through secrets pasted
into a prompt. The org's repositories are listed and cloned in-run through
gateway tools (`github_repositories`, `github_clone_repository`), with
pull-request and issue reads bound to the run's repository. Provider
credentials stay on the trusted side; the sandbox receives what a clone needs,
when it needs it. Details in [GitHub
integration](/platform/github-integration).

## Secrets, injected and announced

Organization secrets configured for the engine's own tooling are injected into
the sandbox environment at run start, and the timeline records a names-only
`secrets.injected` marker. The values are write-only upstream and encrypted at
rest; see [Trust and control](/features/trust-and-control).

## Published outputs are durable

    references with bounded previews, fetched lazily.

  <Card title="Workpieces" icon="file-pen">

The session side rail can expose browser, terminal, files, diff, agents, editor,
and workspace panes when their capabilities are ready. Timeline events,
published artifacts, and recorded patches are durable; live terminal and
desktop connections depend on the retained provider workspace and are not
fully replayed from canonical events. See [Session view](/product/session-view).

:::note
**Honest scope.** The sandbox contract does not expose pause, checkpoint, or
snapshot operations. Continuity comes from the durable thread lease and the
event log, and [recovery](/features/reliability) re-probes and adopts rather
than resuming from a saved image.
:::
